# 第五版基础类目数据维护

## 运行时数据组成

项目仍固定依赖 [`chinese-library-classification==0.0.1`](https://github.com/sheoguo/Chinese-library-classification)，用它保留官网抓取未覆盖的深层类目。`clc_rules/base.py` 启动时再加载 `clc_rules/clc5_base_overlay.json`，以国家图书馆第五版官网可确认节点更新名称和父链。

合并只发生在内存中，不直接修改 `.venv/site-packages`。因此重建虚拟环境后不会丢失更新，也不需要维护一份十余 MB 的第三方包副本。

当前覆盖数据的来源摘要、生成时间和官网地址均写在 JSON 内。导入结果为：

- 原依赖 45,785 条；
- 官网可确认主表覆盖 2,070 条；
- 其中新增 58 条、更新名称 169 条、更新父链 23 条；
- 3 个旧普通号被第五版方括号类目取代；
- 合并后有效基础类目共 45,840 条。

## 为什么不是全量替换

本次树文件自身标记为 `complete: false`，最大抓取深度为 3，虽然没有失败请求和孤立节点，但不能证明所有深层类目已经抓到。若直接用 2,584 个抓取节点替换原依赖，会丢失四万余条仍可用的深层数据。

导入器据此采用以下边界：

1. 只导入主表中以大写字母开头、能够唯一确定的完整分类号。
2. `A1/49`、`K21/27` 等范围或仿分规定不冒充 `A1`、`K21` 的类名。
3. 通用复分表中的 `1`、`2`、`3` 等是各表局部编号，继续由 `tables.json` 与规则引擎处理，不进入全局基础字典。
4. 方括号类目保留括号，例如官网的 `[G07]` 不会被错误转换成普通号 `G07`。
5. 已由纸本规则核对为仿分锚点、不能单独作为图书分类号的 `S50` 不进入基础字典。
6. 官网未出现的深层节点继续使用原依赖数据；不会按分类号逐位截短猜父节点。

这批节点可以修正 `K23`：路径现在显示“古代史中期（公元前475~公元581年）”，不再显示第四版旧类名“封建社会（公元前475~公元1840年）”。但 `K237.105` 尾部的 `05` 属于 `K21/27` 仿 `K20` 的构造规则，不是单一节点；它仍应在复分规则层单独实现，不能靠基础节点文件猜出。

## 重新生成

原始抓取文件不随本项目发布。取得新的树文件和扁平节点文件后，在已安装项目依赖的环境中运行：

```bash
python scripts/build_clc5_base_overlay.py \
  --tree /path/to/clc5_tree.json \
  --nodes /path/to/clc5_nodes.jsonl \
  --allow-incomplete
```

`--allow-incomplete` 是显式安全开关；输入文件标记为不完整时，不加该参数会拒绝生成。生成后可检查结果是否可重复：

```bash
python scripts/build_clc5_base_overlay.py \
  --tree /path/to/clc5_tree.json \
  --nodes /path/to/clc5_nodes.jsonl \
  --allow-incomplete \
  --check
```

每次更新后都应运行全量测试，并重点复核新增号、父链变化、方括号类目和来源摘要。只有当新树文件明确标记完整、深度校验通过后，才可另行评估是否停止使用旧依赖作为兜底。
